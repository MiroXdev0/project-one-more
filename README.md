# Lernzeit — school organizer

Lernzeit is a responsive, shared-workspace organizer for school assignments, presentations, notes, subjects, and files. It uses React, TypeScript, Vite, Express, and Neon Postgres. The workspace is intentionally shared without accounts, as selected for this project; anyone who can reach the API can read and change its data. Deploy it only where that shared access is intended.

## Run locally

Requirements: Node.js 22+ and npm (the backend's Files SDK requires Node.js 22+).

1. Copy `server/.env.example` to `server/.env` and set `DATABASE_URL` to a Neon Postgres connection string.
2. From the repository root, install each app's dependencies if needed:

   ```sh
   npm --prefix server install
   npm --prefix client install
   ```

3. Apply the versioned schema migration (safe to rerun):

   ```sh
   npm --prefix server run migrate
   ```

4. Start the API and frontend in separate terminals:

   ```sh
   npm --prefix server run dev
   npm --prefix client run dev
   ```

Vite proxies `/api` to `http://localhost:3000`. Set `API_PROXY_TARGET` if your local API uses another address. For a separately hosted frontend, set `VITE_API_URL` to the API's origin in `client/.env`.

The app starts with empty states instead of sample data. Create a subject first; assignments, presentations, notes, and files are associated with a subject.

## Configuration

| Variable | App | Required | Purpose |
|---|---|---:|---|
| `DATABASE_URL` | server | Yes | Neon Postgres connection string |
| `PORT` | server | No | API port (default `3000`) |
| `CLIENT_ORIGIN` | server | Production | Exact allowed browser origin(s), comma-separated (Vercel production: `https://schulplan.vercel.app`) |
| `AWS_ENDPOINT_URL_S3` | server | Yes for files | Neon Object Storage endpoint generated by Neon |
| `AWS_REGION` | server | For files | Neon Object Storage region generated by Neon |
| `AWS_ACCESS_KEY_ID` | server | For files | Neon bucket access key; keep server-only |
| `AWS_SECRET_ACCESS_KEY` | server | For files | Neon bucket secret; keep server-only |
| `VITE_API_URL` | client | Production | Public backend origin (for example `https://<backend-project>.vercel.app`); leave empty only for local Vite proxy development |

File uploads use the private Neon Object Storage bucket `uploads`, configured in `server/neon.ts`; the backend accesses it through the Neon adapter in Files SDK. Binary contents are not stored in Postgres. Uploads are limited to 4 MB and checked against supported extensions, MIME types, and file signatures. The limit leaves room below Vercel Functions' 4.5 MB request-body cap for multipart overhead. Download links are private and short-lived. The API reports a clear configuration error until all four generated `AWS_*` variables are set.

The Neon project link (`server/.neon`) and service policy live with the backend so its directory is independently deployable. Run Neon CLI commands from that directory; `neon deploy` applies `server/neon.ts` and pulls Neon-provided environment values into `server/.env.local`. For local server runs and tests, copy `DATABASE_URL` and the four storage variables from that file into `server/.env` (ignored by Git). In Vercel, configure the same generated values on the backend project only; never put storage credentials on the frontend.

## Database and API

`server/src/database/migrations/001_initial.sql` creates the normalized schema and indexes. `npm --prefix server run migrate` records applied migration versions in `schema_migrations`; the DDL is idempotent and existing records are not dropped. Subject foreign keys use `ON DELETE RESTRICT` so a subject with related work cannot be deleted accidentally.

The Express API validates payloads and returns `{ "error": "..." }` for failures:

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/api/health` | Database health check |
| `GET` | `/api/dashboard` | Live summary, upcoming work, recent notes, and subjects |
| `GET`, `POST` | `/api/subjects` | List and create subjects |
| `PUT`, `DELETE` | `/api/subjects/:id` | Update or delete a subject |
| `GET`, `POST` | `/api/assignments` | List and create assignments |
| `PUT`, `DELETE` | `/api/assignments/:id` | Update or delete an assignment |
| `GET`, `POST` | `/api/presentations` | List and create presentations |
| `PUT`, `DELETE` | `/api/presentations/:id` | Update or delete a presentation |
| `GET`, `POST` | `/api/notes` | List and create notes |
| `PUT`, `DELETE` | `/api/notes/:id` | Update or delete a note |
| `GET`, `POST` | `/api/files` | List files or upload multipart field `file` with `subject_id` |
| `GET`, `DELETE` | `/api/files/:id/download`, `/api/files/:id` | Download or delete a stored file |

## Vercel deployment

The UI already deployed at `https://schulplan.vercel.app` and the API are separate Vercel projects. The backend is an Express Vercel Function: `server/src/index.ts` default-exports the existing Express app and only opens a local listener outside Vercel. Vercel's Express framework support routes requests through this application; do not add a competing `/api` catch-all function.

### Backend Vercel project

1. In Vercel, add a project from this GitHub repository (`MiroXdev0/project-one-more`).
2. Set **Root Directory** to `server`. Enable **Include source files outside of the Root Directory** only if the Vercel project requires it; the function and its dependencies are all under `server/`.
3. Use the **Express** framework preset and Node.js 22 or newer. Set **Install Command** to `npm install` and **Build Command** to `npm run build`. Leave **Output Directory** unset; Vercel deploys the Express app as a Node.js Function.
4. Add the backend variables below to the Vercel project's Production environment (and Preview only if you intend previews to use the same shared data/storage).
5. Deploy. The resulting production origin, for example `https://<backend-project>.vercel.app`, is the backend URL. Confirm `https://<backend-project>.vercel.app/api/health` returns `{"status":"ok"}` before proceeding.

Backend Production environment variables:

| Variable | Value |
|---|---|
| `DATABASE_URL` | Neon Postgres application connection string; use the pooled hostname (`-pooler`) for serverless app queries |
| `AWS_ENDPOINT_URL_S3` | Generated by Neon for Object Storage |
| `AWS_REGION` | Generated by Neon for Object Storage |
| `AWS_ACCESS_KEY_ID` | Generated by Neon; keep server-only |
| `AWS_SECRET_ACCESS_KEY` | Generated by Neon; keep server-only |
| `CLIENT_ORIGIN` | Exactly `https://schulplan.vercel.app` |

Set all values in Vercel Project Settings → Environment Variables. Do not commit credentials or put storage/database variables on the frontend.

### Neon schema migration and connectivity

Run the migration from the repository root with a **direct (non-pooled) Neon connection string** available as `DATABASE_URL`:

```sh
npm --prefix server run migrate
```

In PowerShell, set the value for the current terminal before running the command, or copy `server/.env.example` to `server/.env` and replace its placeholder locally. Do not paste credentials into source control or chat. The script records applied migration versions and can be safely rerun. After deploying, check `/api/health`; it performs a live `SELECT 1` through the centralized Neon connection. Do not point migration runs at a pooled hostname.

### Connect the deployed frontend

In the existing `schulplan.vercel.app` frontend project, set **Production** `VITE_API_URL` to the exact backend origin from the backend project's Domains page (origin only, no `/api` suffix), such as `https://<backend-project>.vercel.app`. Redeploy the frontend, because Vite embeds `VITE_API_URL` at build time. The client then calls `<VITE_API_URL>/api/...`; it does not fall back to mock data or an unconfigured same-origin API in production.

The CORS allowlist is configured on the backend using `CLIENT_ORIGIN`. It allows only configured exact origins; without the setting, Vercel defaults to the production frontend origin and local development also allows Vite. CORS controls browser access, not authorization or API access by non-browser clients.

### Verification after configuring Vercel and Neon

```sh
npm --prefix client run lint
npm --prefix client run build
npm --prefix server run build
npm --prefix server test
```

With valid `DATABASE_URL`, the test suite also creates, lists, updates, and deletes a subject, assignment, presentation, and note; it checks that related subjects cannot be deleted and verifies that the dashboard returns persisted data. With the four generated Neon storage variables, it uploads a file, persists and lists metadata, downloads the file using a short-lived URL, and deletes the object and record. Run those integration tests locally only against a non-production Neon branch; the tests create and clean up records/objects. The dashboard/API health checks and CRUD cannot be verified against the deployed backend until its origin is configured.

Because this is a shared, unauthenticated workspace, CORS is not an access-control mechanism. Do not expose the API publicly if its data must be private or restricted to a particular group; choose an authenticated deployment before using it for sensitive student records.

## Checks

```sh
npm --prefix client run build
npm --prefix client run lint
npm --prefix server run build
npm --prefix server test
```

The API tests cover validation, rejected/mismatched file content, request limits, CORS preflight/denial, missing database configuration, and unknown routes without external credentials. Database CRUD integration tests run when `DATABASE_URL` is set and the migration has been applied. File upload/download integration tests require `DATABASE_URL`, all four generated Neon `AWS_*` values, and the private `uploads` bucket.
